# SKILL: Документирование PuzzleAI

Практическое руководство по созданию и редактированию документации PuzzleAI в GitBook-репозитории.

## Когда использовать

Используйте этот скилл, когда нужно:

* добавить новую статью по модели;
* оформить референс трекер-запроса;
* описать параметры no-code API;
* унифицировать стиль страниц в документации PuzzleDocs;
* зафиксировать изменения в changelog.

## Контекст PuzzleAI

* Основной endpoint трекера: `https://api.pxsto.re/main/puzzlebot-tracker`
* Рабочий метод запроса: `POST`
* Вид запроса в PuzzleBot: `Сформированный`
* Формат переменных: `{{VAR}}`
* Обязательная база любого запроса: `bot`, `token`, `user`, `model`
* Основной параметр текста — `prompt`; изображения передаются в `images`, аудио для расшифровки — в `file`, создание документов включается `document=true`.
* `gpt_audio` — ключ распознавания речи, возвращающий текст. Не описывать его как универсальную модель озвучки или диалога.
* Активность, цену и параметры сверять с действующим каталогом; не публиковать отключённые модели как доступные.
* `global` вместе с `type: text/photo/video/music/voice` использует выбранную в плагине модель соответствующего раздела.
* Запрос асинхронный. HTTP-ответ не является готовым ответом модели. Сохранение в `tracker_answer` зависит от настроек; не обещать его безусловно.
* Основные категории моделей:
  * Текст
  * Голос
  * Фото
  * Видео
  * Музыка
  * Другое

## Правила по веткам

* Все изменения делаются только в ветке `main`.
* PR создаются только из ветки `main`.
* Не использовать дополнительные рабочие ветки в этом репозитории.
* Не раскрывать названия внутренних API-шлюзов и апстрим-провайдеров в публичных статьях, примерах, ссылках и changelog. Описывать только продукт, модель и публичные параметры; внутреннюю маршрутизацию называть «внутренний сервис».

## Структура страницы модели

Каждая страница модели должна содержать следующие разделы:

1. `# Название модели`
2. краткое описание назначения модели
3. `## Как отправлять запрос`
4. `## Пример запроса с комментариями`
5. `## Параметры`
6. `## Ответ`
7. `## Важно` при необходимости

## Шаблон статьи

````markdown
# model_name

Коротко опишите назначение модели и тип задач.

## Как отправлять запрос

- Ссылка: `https://api.pxsto.re/main/puzzlebot-tracker`
- Метод: `POST`
- Вид запроса в PuzzleBot: `Сформированный`
- Формат тела: `application/json` или те же ключи в no-code параметрах.

Обязательная база для любого запроса: `bot`, `token`, `user`, `model`.

## Пример запроса с комментариями

```jsonc
{
  "bot": "{{BOT_USERNAME_TEXT}}", // обязательно: username бота в PuzzleBot.
  "token": "[Ваш API-токен]", // обязательно: API-токен бота.
  "user": "{{USER_ID_TEXT}}", // обязательно: ID пользователя или сессии.
  "model": "model_name", // обязательно: точный ключ модели.
  "prompt": "{{prompt}}", // обычно обязательно: текст задачи; исключения описываются в статье модели.
  "role": "[текст роли]", // необязательно: роль, стиль или ограничения.
  "send_answer": true // необязательно: отправить результат пользователю.
}
```

## Параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `bot` | string | Да | Username бота: `{{BOT_USERNAME_TEXT}}`. |
| `token` | string | Да | API-токен бота. |
| `user` | string | Да | ID пользователя: `{{USER_ID_TEXT}}`. |
| `model` | string | Да | Точный ключ модели. |
| `prompt` | string | Зависит от модели | Текст задачи. |
| `role` | string | Нет | Дополнительная инструкция. |
| `send_answer` | boolean | Нет | Отправлять ли результат пользователю. |

## Ответ

Запрос выполняется асинхронно. Опишите доставку результата в чат и получение `tracker_answer` после завершения с учётом настроек сохранения.
````

### Стиль сообщений в Telegram

* Один выпуск — одно короткое сообщение. Общий заголовок: `Px.AI — обновления`, затем период. Название Студии использовать только в соответствующем подразделе, не как название всех обновлений продукта.
* Использовать Telegram HTML: `<b>` для заголовка и названий разделов, `<i>` для периода, `<a>` для одной ссылки «Все изменения» на ченджлог. Экранировать пользовательский текст; не отправлять сырые Markdown-звёздочки. Отключать предпросмотр ссылки.
* Группировать пункты по изменившимся разделам продукта и писать, что теперь может сделать пользователь. Не выводить пустые разделы, длинные технические списки, внутренние названия, SHA, ключи задач или журналы публикации в публичном анонсе.
* Важные исправления объединять в короткий блок «Исправили». Короткие абзацы и списки, не более одного-двух уместных эмодзи; не украшать каждую строку и не писать заголовок капсом.
* Личный черновик владельцу имеет заголовок «Px.AI — на согласование», период и номер версии. Сам анонс показывать в том же оформлении, в котором он уйдёт в Саппорт. Кнопки «Одобрить» и «Доработать» размещать в одной строке; служебную подсказку о действиях оставить в личном сообщении, не переносить в публичный анонс.
* Если меняется только оформление уже доставленного текста, редактировать существующий message_id. Не дублировать сообщение, не отправлять новое уведомление и сохранять закреп. Изменение смысла после одобрения требует новой версии согласования.

* Пишите коротко, по делу, без «воды».

* Не смешивайте русский и английский в именах параметров.
* Всегда явно разделяйте обязательные, необязательные и условные параметры.
* В комментированном примере добавляйте `//`-комментарий к каждому параметру.
* Если формат ответа не подтверждён, явно укажите это.
* Все примеры должны быть воспроизводимыми.
